# 招聘领域不变量

## 核心主语

- `Candidate` 是自然人，不保存全局“淘汰/录用”结果。
- `Resume` 是逻辑简历，`ResumeVersion` 是不可覆盖的原始文件版本；评分、发送、解析和证据必须绑定具体版本。
- `Application` 是候选人与招聘需求的关系；流程阶段、未通过、录用、退出只属于该记录。Application 不存在 `HOLD`/暂缓状态，招聘耗时只按最初创建至最终终止的总自然时间计算。
- `OfferStatusRecord` 属于 Application，固定为 `NOT_STARTED/IN_PROGRESS/ISSUED/ACCEPTED/TERMINATED/ONBOARDED` 六态；谈薪和审批都属于 `IN_PROGRESS`，终止原因必填并原子映射 Application 结果，带原因的 reopen 可从 `TERMINATED` 恢复同一 Application，`ONBOARDED` 只能由真实 `OnboardingEvent` 产生。
- `ClientSubmission` 是外派推荐独立聚合，绑定客户、项目、岗位和发送时的简历版本。
- JD、评分方案、解析结果、AI 运行、面评和关键状态都保留版本或快照；修正采用追加/失效，不抹除历史。

## AI 评分与风险

评分结果必须分为五条通道，禁止只保存一个总分：

1. 受控条件：年龄、性别、学历、证书、语言按 `MUST/PREFER/DISPLAY_ONLY` 和满足/未知/不满足展示；未知不等于失败。
2. 五维基础分：核心技能、岗位经历、相关年限、职责匹配、行业与项目原始分与证据独立保存，五维权重版本化后计算 0～100 分。
3. 附加分与综合参考分：`PREFER` 单项只允许 5/10/20 分，官方方案合计不超过 30；满足才加分，未知/不满足不加不扣；基础分、附加分/当前选中上限和综合参考分必须分开展示。
4. 突出项：允许某一专项极强但综合分一般的候选人被单独召回，标签本身不重复加分。
5. 风险：疑似造假、多简历事实冲突、黑名单、禁推、证据不足等提示。

每个判断同时保存证据引用、模型置信度、模型与提示词版本；模型置信度不等于准确率或证据覆盖率。官方条件方案和个人权重/偏好选择分别版本化；个人不能关闭官方 `MUST`。年龄、性别只读取显式或 HR 核实事实，不从姓名、照片或代理变量推断。AI 分别按 JD/简历版本提取事实和证据，再对两侧冻结事实进行五维专业评分，保存不可变的原始分、默认专业分、理由及双侧证据。Java 仅复用已有 AI 原始分按自定义权重重算，并处理独立受控条件、附加分与稳定排序，不得恢复关键词或年限规则评分。调整权重/偏好不重复调用模型；评分缓存按 JD/简历事实快照、评分提示词和 Schema 版本隔离，日期、权重和当前模型配置变化不覆盖既有判断。模型失败不得回退规则评分；历史算法结果保留原版本，不冒充 AI。系统不自动拒绝。

## 流程与协作

- 全部内部/外派招聘都按确定 JD 版本绑定受控流程模板，不引入通用 BPM；模板只定义允许步骤和顺序，活动实例继续使用创建时模板版本。只有该 JD 版本的流程模板和正式评分配置都为 `ACTIVE` 才能创建 Application 和正式评分，任一缺失时只保存 JD 草稿且不得产生步骤/评分任务/Outbox。HR 为每条 Application 单独选择实际沟通/面试路径，采用沟通时默认电话；客户推荐/甲方 AI 面试人工记录步骤只允许外派模板。
- 模板必须恰好包含一个不可选的 `DECISION`。候选人采用的步骤进入活动态，未采用的可选步骤记为 `NOT_SELECTED` 且不生成待办、deadline 或跟进要求；每个实际执行步骤必须有负责人、截止时间、有效跟进/反馈和结构化结果。`SKIPPED` 只用于已开始步骤的带专门权限、原因和审计的事实纠错，不能代替普通选路。
- 每条 Application 都必须保存人工招聘决定的操作者、时间、`PASS|REJECT|WITHDRAW` 和非空简短原因，只有 `PASS` 可进入 Offer。决定更正只追加；Offer 尚未开始且 Application 未终止时可带原因更正，之后必须先受控纠正状态或 reopen。外派 Application 进入甲方 AI/甲方面试或提交 `PASS` 决定时必须绑定确切 `clientSubmissionId`，并校验推荐 `deliveryStatus=SENT`、`sentAt` 非空且与当前 Application、甲方、JD 和发送 ResumeVersion 一致；甲方处理状态不得覆盖发送事实，撤回后不可继续使用。
- JD 目录使用权限裁剪的服务端游标；候选人、Application、面试、客户推荐、工作台、报表和导出共享同一 `jdId/jdVersionId` 过滤语义。逻辑 JD 默认覆盖历史版本，精确版本只用于相应快照。
- 甲方 AI 面试只允许 HR 人工代录客户侧外部流程事实并保存记录人、反馈渠道和来源；本系统不定义供应商端口、适配器、回调、模型调用或自动判断，不发起、不实施且不对面试服务/结果负责。
- 流程模板由 JD 需求负责人、显式协作人或管理员配置的管理范围内领导创建、修改和激活，保存实际操作者和时间；`SUPER_ADMIN` 可操作全部 JD。历史敏感事实只能追加更正。新版本只作用新 Application；未来 P1 迁移仅可由超级管理员 dry-run、带原因执行并追加逐条审计。
- 正式黑名单只设公司级；普通 HR 可新增、更正、停用，任何角色都不能删除。新增要求原因及来源/证据，停用要求原因，提交后立即阻断新联系、新建 Application、客户推荐和非终止推进并列出所有受影响活动流程；不得自动批量淘汰或生成决定，HR 逐条提交带原因的 `REJECT/WITHDRAW`。普通甲方拒绝只结束当前推荐；拒绝页仅在显式勾选 `DO_NOT_SUBMIT/CLIENT_EXPLICIT_BAN` 且原因/来源完整时原子创建默认永久、仅影响对应甲方的限制，未勾选或字段不全不得创建；甲方 A 不阻断甲方 B。停用账号前的交接和非评分学历标签规则保持不变。
- 阶段迁移同时追加历史；迟到事件不能让状态倒退。未开始的候选人路径选择可由负责人/协作人带原因追加修改；已开始步骤必须以 `WITHDRAWN` 结束后再选路，完成事实不能回退，`SKIPPED` 只用于错录纠正。进入甲方筛选/面试后撤回推荐必须填写原因，并在同一短事务把推荐和当前甲方步骤记为 `WITHDRAWN`；原推荐不能继续用于甲方步骤/PASS，HR 重新选路后仍需提交人工决定。任一人工决定及其更正记录操作者、时间、理由和来源。
- Offer 状态、更正和外部人事系统映射只追加历史；更正指向原记录并重建当前投影，禁止覆盖或删除原事实。重复人工命令、导入和未来外部回调必须幂等。
- 候选人跟进锁默认七天，只由候选人回复、Application 推进、面试安排/完成、客户推荐发送或 Offer 推进续期；浏览和普通备注不续期。
- 个人超时阈值只影响本人的提醒/deadline，不改变阶段事件或招聘总耗时；候选人沟通、全部面试、甲方反馈和 Offer 复用现有五类映射，V1 不建立按 JD SLA。导出覆盖当前全部可见结果，按每文件 100,000 行拆分、七天过期、每用户最多两个活动任务，且始终复用查看判定。
- 一般风险由有权限 HR 本人确认或带风险推进并持续留标，不建设领导审批链。
- 正式面评对当前 Application 的授权参与者可见；草稿仅作者可见，HR 私密/薪酬备注受字段权限控制。
- 普通甲方拒绝只结束当前推荐；甲方明确禁推/以后不再考虑时，由 HR 在原因、来源完整后显式创建客户级且可有有效期的限制记录，不污染 Candidate 全局状态。项目和岗位只作为来源上下文，不改变客户级生效范围；重新推荐前统一求值并给出可解释提示。

## 权限与重复识别

最终访问判定为：`RBAC 动作权限 ∩ 数据范围 ∩ 对象授权 ∩ 字段/高风险动作权限`。

- 搜索索引中的权限主体只做召回前过滤；详情、下载、导出和高风险动作必须回查 MySQL 权限事实。下载/导出不设独立权限码，只能输出对应查看判定允许的对象与字段交集。
- 内置 `admin` 初始持有不可删除、不可收窄的 `SUPER_ADMIN` 系统角色；该角色可授予多个 `ACTIVE` 账号，所有持有人均可访问全部系统与招聘业务数据和动作。授权、撤销和停用全审计，并始终至少保留一个在用超级管理员；不得按用户名硬编码权限。
- 超级管理员仍必须执行对象状态、版本、幂等、数据完整性和审计约束；其他平台/业务角色继续按最小必要权限分离。
- 正式 JD 评分配置只由 `SUPER_ADMIN` 持有人在后台维护；普通 HR 不维护条件草稿。同一 JD 版本最多一个 `ACTIVE` 配置，变更复制新版本且只影响后续任务，历史评分不自动重跑。
- 无完整权限者命中疑似重复候选人时，只返回脱敏存在性、归属团队和最近联系时间范围，并提供访问申请/联系负责人入口。
- 候选人身份合并、拆分和多简历冲突必须可回滚、可审计；不得仅按姓名自动合并。
- 当前从零建库，不实现既有招聘系统历史迁移、旧招聘台账回放或 JD/甲方/ResumeVersion 人工关联；账号/配置初始化和新简历批量上传不得创建历史 Application、决定、甲方限制或公司黑名单。
- 客户、客户项目、客户岗位和来源渠道是运行主数据，由获授权 HR 日常创建、修改和停用，`SUPER_ADMIN` 全量兜底。编码稳定唯一；被需求、收件、推荐或报表引用后不得删除，停用记录保留历史含义但不能用于新业务。真实初始数据在制品交付后配置，不得写入 Java/Flyway 常量。
