# HR AI 变更验证

证明本次后端改动满足行为、架构和集成边界；不要把“看起来正确”当成测试证据。

## 先确定验证对象

1. 读取适用的 `AGENTS.md` 和相关生产代码、测试；仅在确认命令、模块或构建配置时读取根及改动模块的 `pom.xml`。同一会话已读且未变化的内容不重复读取。
2. 从本轮实际修改或用户指定的 diff 确定范围。工作区存在其他未提交改动时，不把它们冒充为本轮成果，也不清理、覆盖或回退它们。
3. 列出受影响模块、公开契约、模块边界、数据库/消息/外部系统边界和必须保持的业务不变量。
4. 修复缺陷时确认回归测试曾因原缺陷失败；新行为必须有直接行为测试。验证请求本身不授权无关重构。

## 选择验证层级

按需读取 [验证矩阵](references/verification-matrix.md) 的适用行，按改动风险选择最小充分验证。调试时可先跑聚焦检查；最终验证按实际覆盖选择命令，无需机械逐层运行。不要用 mock、编译成功或单个 happy-path 测试替代所需层级。

始终遵守：

- 验证须覆盖受影响行为、模块及其依赖；涉及模块/API/包边界时包含 `contract-test`。上层命令已实际执行并通过所需测试或门禁时，可替代下层命令，不要求重复运行。
- 面向可合并后端代码的完成声明通常需要根目录 `clean verify` 的最新成功证据。若成本、环境或用户范围使其未运行，准确报告为“局部验证通过”，不得说整个仓库通过。
- MySQL/Flyway/MyBatis、Broker、搜索、对象存储或模型供应商兼容性不能只靠内存替身证明。只连接显式授权的隔离测试环境；本机可丢弃中间件可按本地运行指南由使用者启动，不得自动操作共享或生产服务，不得猜测或输出凭据。
- 测试失败时保留完整的首个应用侧根因和退出码。若原任务授权实现，可修复范围内回归并重新验证；否则只报告，不擅自修改。
- 不通过跳过测试、删除断言、放宽架构规则、更新快照或扩大容差来制造绿色结果。

## Ponytail 边界

仓库架构、领域不变量和测试要求高于通用最小化规则。“最小改动”是满足这些边界后的最小实现，不得仅为减少文件或行数而：

- 合并模块、绕过窄 API/端口或让模块直接访问其他模块内部实现；
- 混用 Request、Response、DTO/Command/Query 和 Entity；
- 删除权限、校验、幂等、并发、审计、失败恢复或契约测试；
- 把必要的模块/供应商端口误判为“单实现接口所以应内联”。

## 交付证据

最终报告必须区分：

- **已通过**：命令、范围、退出码和可核对的测试/模块结果；
- **失败**：首个根因、受影响范围，以及是否由本轮改动引入；
- **未运行**：缺失环境、凭据、服务、时间或不在本次范围等客观原因；
- **结论边界**：只能从实际证据推导，例如未跑外部 MySQL 就不能声称迁移或方言兼容。

使用本任务、同一相关源码与配置状态下可核对的命令、退出码和原始测试报告；允许复核其他 Agent 提供的完整证据，不接受未经核验的成功声明或状态不明的旧日志。相关代码、配置或测试环境变化后重跑受影响检查。没有足够证据时，明确写“尚未验证”。
