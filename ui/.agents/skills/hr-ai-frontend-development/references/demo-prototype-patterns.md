# VGO 演示原型模式

本参考用于只读演示、交互原型和无后端 Mock 页面，保留已移除品牌原型的视觉与交互经验；生产应用仍以 React/TypeScript/Ant Design 规范和 OpenAPI 契约为准，不能复制原型中的静态业务数据。

## 1. 使用边界

- 演示页面只使用模块内常量与 React 本地状态，不发起 API 请求，不伪造联调、同步或外部平台连接成功。
- 页面显式标识“演示数据 / 不连接后端”；候选人、客户、组织、金额、时间和结果均为虚构样例。
- 既有演示功能优先保持结构与行为不变。新增能力先寻找同页入口，以按钮、对话框、抽屉或页内二级导航扩展，避免改写稳定的四主域导航。
- 甲方 AI 面试始终写作“外部流程·人工记录”；不能出现供应商连接、自动面试、自动回调、系统验证或自动通过。
- AI 匹配是辅助证据，不是录用结论。任何推荐、风险和评分附近都保留 HR 确认、修正、忽略或继续处理入口。

## 2. 视觉继承顺序

新增区域按以下顺序取视觉依据：

1. 同一页面已有组件和密度；
2. `DESIGN.md` 的令牌、布局和命名规则；
3. 本参考的原型模式；
4. 只有前三者都没有覆盖时才新增样式，并保持“可信招聘运营台账”的克制语气。

不要为了显得高级而引入渐变大标题、玻璃拟态、巨型圆角、装饰图表、发光、悬浮卡片阵列或新的强调色。高级感来自稳定列宽、信息层级、精确间距、上下文状态和完整演示数据。

## 3. 画布、排版与密度

- 工作区底色为 `#F8FAFC`，普通数据面板为白色；正文使用深靛青 `#17233F`，次要文本使用 `#64748B`。
- 人工主操作使用 `#0F766E`，Hover 使用 `#0B5F59`；`#10B981` 只表达完成/确认，不代表 AI 自动录用。
- 结构边界用 `#DCE5EE`，内部细分隔线用 `#E9EEF4`。普通台账面板不加阴影；只允许首页概览卡、主要动作、Toast 和浮层使用受控阴影。
- 中文系统字体为 `PingFang SC / Microsoft YaHei / Noto Sans SC / system-ui`。页面标题约 24–27px，区块标题 16–19px，正文 12–13px，表头/元数据 10–12px，指标数字 23–26px。
- 控件通常 36–42px 高；密集数据行约 56–74px。面板圆角 8–12px，字段 6–7px，状态标签 4–5px；状态标签不做无意义药丸。
- 页面宽屏左右留白通常 44–48px；在 1500px、1250px、900px 逐级压缩。页面本身不横向滚动，表格、日历、评分矩阵和看板在自身边界内滚动。

## 4. 已建立的组件原型

### 页面头

- 左侧：页面标题、对象上下文或可搜索 JD 触发器；紧邻一行简短状态/说明。
- 右侧：最多一个主动作，其他动作为次按钮或文本动作。
- 需要说明演示边界时，使用低饱和信息条，不使用营销 Banner。

### 指标条

- 3–5 个同宽指标，数字 + 明确中文标签 + 必要的趋势/待办说明。
- 指标可点击时提供选中边框、`aria-pressed` 和可读筛选结果；颜色始终配标签。
- 用于筛选或下钻的指标必须由当前列表派生。若需要展示全局演示口径，可以使用静态假数据，但必须明确标注“全局演示口径 / 下方为代表样例”，不得伪装为可点击筛选，也不得与当前列表合计混用。

### 过滤与数据台账

- 搜索、结构化筛选、重置和批量动作置于同一水平工具条；窄屏允许工具条局部横向滚动或换行。
- 表头低对比、数据列对齐稳定，数字使用等宽数字。姓名/对象列和批量选择可按需要 Sticky。
- 每个列表至少提供 4–7 条差异明显的假数据，覆盖正常、待确认、异常、部分成功、已完成或受限状态。
- 表格上方显示筛选结果数量、当前排序、版本或数据口径；分页、选择数量和批量动作保持可见。

### 状态分层与简化

- 先区分三个层次：对象的正式业务状态、页面的处理分组、风险/权限/通知等附属事实。不要把三者塞进同一个状态枚举。
- 页面级筛选可统一为“处理中 / 需处理 / 已结束”等少量互斥分组，但行内仍展示该对象在正式状态机中的真实状态；同一记录不能同时计入两个处理分组。
- 候选人没有全局录用、淘汰、风险或转交状态。岗位结果属于 Application；跟进锁、字段脱敏、简历冲突、内部备注和交接分别用标签、事实区或任务显示。
- 招聘需求只使用草稿、启用、暂停、关闭；JD 解析待确认、评分配置待激活和流程模板待发布是关联待办，不扩展需求状态。
- 面试主状态保持已安排、已结束、已取消等生命周期；候选人确认、时间冲突、通知发送和面评提交是附属事实。任务状态也不使用“可下载/链接过期”，这些属于导出产物状态。
- 客户推荐状态与推荐前检查分开：冷却、甲方限制、公司黑名单和部门内部备注都不是推荐状态。部门谨慎联系只能是不阻断的内部备注，不得展示为部门黑名单或正式限制。
- 匹配记录状态与推荐类别分开：待复核、已复核、已过期描述记录生命周期；强推荐、单项突出、UNKNOWN 和风险用类别/标签/证据区表达。

### 证据与时间线

- AI 结果拆为：五维/条件、证据节选、覆盖率与可靠性、风险/未知、规则版本、人工处理。
- `UNKNOWN` 写“未找到充分证据”，可说明计算贡献为 0，但不得显示为不通过。
- 流程时间线固定展示步骤状态、负责人、截止时间、最后有效跟进、结果和下一步。未启用步骤不制造空待办。
- 更正、重新开启、跳过和带风险推进均追加历史记录，不把旧事实从演示时间线中删除。

### 对话框与抽屉

- 创建、编辑、确认和高风险操作使用聚焦对话框；跨多个信息分区的详情使用右侧抽屉或整页覆盖层。
- 对话框标题说明对象和动作，正文先给影响摘要，再给字段；底部为取消 + 单一主动作。
- 关闭后焦点返回触发按钮；支持 Escape、遮罩关闭（高风险确认除外）和清晰的键盘焦点。
- 表单提交只修改本地状态并显示 Toast。演示应包含校验、禁用、冲突或必填原因等至少一种可见状态，而非所有按钮都只弹“成功”。
- “查看详情/完整档案/功能演示”等按钮必须打开可检查的数据面，至少包含多行明细、版本/证据/权限中的一种，以及一个会产生可见本地结果的操作；不得只显示 Toast。

## 5. 全需求演示页的信息架构

当需要在一个页面集中展示完整产品能力时，保留四个既有主导航，并从页头/更多能力入口进入“业务全景”。页面内部使用紧凑的业务域导航，推荐顺序：

1. 招聘需求与 JD；
2. 收件与批量导入；
3. 候选人档案；
4. 匹配与评分；
5. Application 流程；
6. 面试与面评；
7. 客户推荐与限制；
8. Offer 与入职；
9. 任务、导出与报表；
10. 组织、权限与审计。

每个业务域至少包含：一组可下钻指标、一组可筛选多行数据、一个详情/时间线区域，以及一个能改变本地状态的主要交互。不要把全部需求压成大量互不相关的卡片。

## 6. 演示数据最低要求

- 名称、JD 编号、版本、客户/部门、项目、负责人、截止时间、渠道、来源、状态和原因使用彼此一致的跨模块引用。
- 同一候选人在不同 JD 下必须展示独立 Application、评分和结果；候选人本身不使用全局“淘汰/录用”。
- 批量任务至少覆盖运行中、部分成功、失败可重试、已完成/链接将过期；显示总数、成功、重复/冲突、失败和待人工数量。
- Offer 数据覆盖六态；终止样例包含原因，更正样例保留原记录，入职样例包含真实事件时间与来源。
- 客户推荐至少覆盖可发送、冷却提示、部门限制、公司级禁推或重复推荐证据；一般风险继续推进要求原因。
- 权限样例覆盖招聘专员、招聘负责人/领导、面试官和 `SUPER_ADMIN`，同时展示字段脱敏或只读状态。

## 7. 状态与交互检查

纯演示页面也需要在可见范围内表现以下状态，而不是假定后端存在：

- initial / success / empty / filtered-empty；
- partial-success / failed / retrying / cancelled；
- field-redacted / forbidden / read-only；
- version-conflict 或“数据已更新，请重新确认”；
- long-task-running / terminal；
- 受控条件 UNKNOWN、风险待确认和人工覆盖理由。

跨域全景还应优先让以下需求形成可见效果，而不是只写在说明中：JD 版本差异和影响预览、附件级导入结果和隔离原因、简历版本事实差异与字段权限交集、五维证据定位与 AI 反馈、流程步骤实例与有效跟进门禁、通知预览与本人面评、推荐前检查矩阵与结构化甲方反馈、Offer 来源/更正/重开、任务逐项结果与报表口径、离职交接与最后超级管理员保护。

验证时至少检查 390、1280、1800px：页面无横向溢出，局部滚动保留上下文，弹窗不超出视口，主功能能用键盘完成，状态不只依赖颜色，减少动画偏好有效。
